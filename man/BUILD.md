# Building CCCC

How to build the `cccc` binary from a source checkout. For writing `build.c`
scripts for your *own* projects, see [BUILD_MODE.md](BUILD_MODE.md).

## Prerequisites

- A host C compiler (`cc` / `clang` / `gcc`) and `make`.
- **libffi** — required, for the VM's foreign-function interface.
  - macOS: ships with the system / Xcode CLT.
  - Linux: `apt install libffi-dev` (or your distro's equivalent).

Everything else is optional and probed at build time:

| Optional dependency | Enables | Notes |
|---|---|---|
| GNU **readline** | line editing/history in the REPL | probed via `pkg-config`; Homebrew fallback on macOS |
| **libbacktrace** | symbolic host C stack traces on a crash | vendored in `src/backtrace/`, **on by default** |
| **libcurl** | URL `#include`/`#embed` and URL-aware `__has_include`/`__has_embed` | off by default |
| **doxygen** (+ graphviz) | the HTML API docs (`docs` target) | off by default, never part of a normal build |
| Intel **BID** library | `_Decimal32/64/128` decimal floating-point | never vendored; fetch first (see below) |

## Two binaries

There are **two** `cccc` binaries and they can go stale independently:

| Command | Produces | Contents |
|---|---|---|
| `make` | repo-root `./cccc` | stage0 — no libbacktrace, no readline |
| `./cccc --build build.c --build-target=cccc` | `build/cccc` | full build |

`./cccc --build build.c` does **not** rebuild `./cccc` itself. After changing
C sources, run `make` too (or `--build-target=test`, which rebuilds `./cccc`)
before trusting the standalone smoke scripts, which hardcode the repo-root
`./cccc`.

## Quick build

```sh
make                       # stage0 ./cccc
./cccc --build build.c     # full build system takes over from here
```

On a **fresh clone** the embedded stdlib table `src/std.c` does not exist yet,
so bootstrap once:

```sh
make bootstrap             # stage0 -> regenerate src/std.c -> relink
./cccc --build build.c     # its own two-pass regen is a no-op from here on
```

`make -f tools/Makefile.backup <target>` is the pre-cut full-featured Makefile,
kept as an escape hatch for when there is no working `cccc` yet.

## Optional feature knobs (`CCCC_HAS_*`)

A few guest-visible features are off by default because they pull in an extra
host dependency. Each is gated behind a `CCCC_HAS_*` environment variable read
by `build.c` (and mirrored in `tools/Makefile.backup`):

| Env var | Feature | Extra dependency |
|---|---|---|
| `CCCC_HAS_CURL=1` | URL-based `#include`/`#embed` directives and URL-aware `__has_include()`/`__has_embed()` probes; fetch knobs `--url-cache-dir`, `--url-cache-clear`, `--url-timeout`, `--url-max-size` | `libcurl` |
| `CCCC_HAS_DECIMAL=1` | `_Decimal32/64/128` via the Intel BID library | never vendored — run `tools/fetch_intel_bid.sh` first |
| `CCCC_HAS_NDBM=1` | `<ndbm.h>` on Linux (macOS/BSD have it natively) | `libgdbm-compat-dev` (links `-lgdbm_compat`) |
| `CCCC_HAS_BACKTRACE=0` | opts *out* of the vendored libbacktrace | on by default |

```sh
CCCC_HAS_CURL=1 ./cccc --build build.c --build-target=cccc
tools/fetch_intel_bid.sh && CCCC_HAS_DECIMAL=1 ./cccc --build build.c
```

## Selecting the toolchain

- `CCCC_BUILD_CC` (else `cc` / `clang` / `gcc`) selects the compiler that
  builds `--build` targets, including `cccc` itself. `CCCC_BUILD_AR` (else
  `ar`) selects the archiver.
- This is separate from `CCCC_NATIVE_CC`, which only selects the compiler
  `-c=native` hands its *generated* C to.
- A real gcc is supported, e.g. on macOS:
  `CCCC_BUILD_CC=/opt/homebrew/bin/gcc-16 ./cccc --build build.c --build-target=cccc`.

## Generated files

Some sources are generated. Two are committed (so a plain `make` needs no
`python3`); one is a build artifact and must never be committed:

| File | Committed? | Regenerated by |
|---|---|---|
| `src/std.c` | **no** — gitignored artifact | `./cccc --build build.c` two-pass build (or `sh tools/regen_stdlib.sh <cccc>`) |
| `src/reflection_ffi_protos.inc` / `src/reflection_ffi_register.inc` | yes | `tools/gen_reflection_ffi.py` (run automatically by `--build`) |
| `src/shims.inc` | yes | `tools/gen_shims.py` (run automatically by `--build`) |

`./cccc --build build.c`'s default build is two-pass: a stage-1 `cccc` is
compiled against whatever `src/std.c` is on disk, uses it to regenerate
`src/std.c` from `tools/generate_stdlib.c`, then the real `cccc` is recompiled
against the fresh table — so `src/std.c` can never go stale. A fresh clone
with no `src/std.c` links against the committed `src/std_stub.c` stand-in
(empty table) until `make bootstrap` produces the real one.

`tools/gen_reflection_ffi.py --check` and `tools/gen_shims.py --check` catch
staleness of the committed `.inc` files and are wired into the `test` build
target.

## Build targets

`build.c` covers what used to be Makefile targets. A few common ones:

| Target | What it does |
|---|---|
| `cccc` | full `build/cccc` |
| `test` | rebuild `./cccc`, run the whole test suite (this is the self-consistent one) |
| `docs` | Doxygen HTML for the three public headers into `build/docs/html/` (needs `doxygen` + `graphviz`) |
| `cccc_asan` / `cccc_ubsan` / `cccc_tsan` / `cccc_msan` / `sanitizers` | sanitizer builds |
| `afl` / `afl_asan` / `fuzz_harness` | fuzzing binaries |
| `libcccc` | shared/static library |
| `clean` | remove build outputs |

```sh
./cccc --build build.c --build-list-targets   # list them all
```

The published API docs are at <https://takeiteasy.github.io/cccc/>; the `docs`
output is gitignored and regenerated locally on demand.
